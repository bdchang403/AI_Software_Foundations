# Module 1: Infrastructure as Code Directives & State Traceability Contracts

## 🧠 Theory: Strict Bounds for State Traceability and Infrastructure Guardrails

In application development, an artificial intelligence hallucination generates a software defect. In infrastructure and deployment operations, an artificial intelligence hallucination generates **State Corruption, Security Exposure, and Cloud Financial Waste**.

If an engineer asks an AI model: *"Write Terraform code to deploy an S3 bucket and database,"* without supplying context boundaries, the model will invent arbitrary CIDR blocks, grant public internet ingress, omit encryption keys, or create un-tracked cloud resources. In cloud environments, un-tracked infrastructure leads to security breaches and runaway cloud bills.

To prevent infrastructure drift and security breaches, BuilderOps teams write **Declarative and Defensive 3-Part Directives**:
1. **Context Boundary**: The exact cloud provider, environment constraints, network topology, and security rules.
2. **Task Instruction**: The explicit resource declarations, lifecycle policies, and backup configurations.
3. **Format & Safety Constraints**: Mandatory encryption, private subnet isolation, zero hardcoded credentials, and automated rollback tags.

### ✅ The Sovereign Directive (Defensive 3-Part Pattern)

```markdown
### 1. CONTEXT BOUNDARY
- SPECIFICATION: `docs/infra/HEALTHCARE_DATASTORE_SPEC.md`.
- NETWORK ISOLATION: Place strictly within `module.vpc.isolated_data_subnets`.
- COMPLIANCE STANDARDS: HIPAA Security Rule (45 CFR § 164.312) and Enterprise AI Constitution.

### 2. TASK INSTRUCTION
Define an `aws_db_instance` and an `aws_s3_bucket` for encrypted clinical record storage:
- Database must run PostgreSQL 16.2 with multi-AZ failover enabled.
- S3 bucket must enforce object versioning and default server-side encryption via AWS KMS.
- Apply AWS lifecycle configuration migrating objects to Glacier Flexible Retrieval after 90 days.

### 3. FORMAT & SAFETY CONSTRAINTS
- SECURITY INVARIANT: `publicly_accessible = false` on database; `block_public_acls = true` on S3.
- ENCRYPTION INVARIANT: `storage_encrypted = true` using `aws_kms_key.patient_data_key.arn`.
- SECRET INTEGRITY: Passwords must reference `var.db_password` via AWS Secrets Manager.
```

### 📜 The Verified Generated Code: `clinical_datastore.tf`

```hcl
# Verified against HIPAA Security Rule & Enterprise AI Constitution
resource "aws_db_instance" "clinical_records_db" {
  identifier                  = "clinical-records-prod-db"
  allocated_storage           = 100
  max_allocated_storage       = 500
  storage_type                = "gp3"
  engine                      = "postgres"
  engine_version              = "16.2"
  instance_class              = "db.m6i.large"
  multi_az                    = true
  
  # Network Boundary Isolation
  db_subnet_group_name        = aws_db_subnet_group.isolated_data.name
  vpc_security_group_ids      = [aws_security_group.db_access_from_app.id]
  publicly_accessible         = false

  # Cryptographic Security & Secrets Governance
  storage_encrypted           = true
  kms_key_id                  = aws_kms_key.clinical_data_key.arn
  username                    = "clinical_admin"
  manage_master_user_password = true # Uses AWS Secrets Manager natively

  # Disaster Recovery & Immutability
  backup_retention_period     = 30
  deletion_protection         = true
  skip_final_snapshot         = false
  final_snapshot_identifier   = "clinical-records-final-snapshot"

  tags = {
    Environment     = "production"
    DataClass       = "PHI"
    GoverningEpic   = "EPIC-HEALTHCARE-804"
    AITrailerDigest = "sha256:d83a1b9c"
  }
}

resource "aws_s3_bucket" "clinical_documents" {
  bucket        = "clinical-documents-encrypted-vault"
  force_destroy = false

  lifecycle {
    prevent_destroy = true
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "clinical_s3_encryption" {
  bucket = aws_s3_bucket.clinical_documents.id

  rule {
    apply_server_side_encryption_by_default {
      kms_master_key_id = aws_kms_key.clinical_data_key.arn
      sse_algorithm     = "aws:kms"
    }
  }
}

resource "aws_s3_bucket_public_access_block" "clinical_s3_block" {
  bucket = aws_s3_bucket.clinical_documents.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

## 🌐 Dual-Use Regulated Comparison: IaC Directives Across Critical Sectors

| Directives Parameter | Healthcare / Medical Device (FDA SaMD Cloud Backend) | Banking & Core Transaction Mainframe |
| :--- | :--- | :--- |
| **Network Isolation** | Database and telemetry workers must be placed inside air-gapped VPCs without internet gateways; clinical data egress is blocked. | Database servers reside in strictly peered private subnets; external internet routing tables are forbidden by routing policy. |
| **Data Encryption** | FIPS 140-2 validated encryption in transit (TLS 1.3) and at rest (AES-256 via customer-managed KMS keys) with automated key rotation. | Hardware Security Module (HSM) key derivation for all database tables and transaction message queues. |
| **Disaster Recovery** | Cross-region read replicas with Continuous Data Protection (CDP) asserting Recovery Point Objective (RPO) $\le 15 \text{ minutes}$. | Synchronous write-ahead log mirroring across dual active-active data centers asserting RPO = 0 and RTO $\le 60 \text{ seconds}$. |
| **Lifecycle Deletion** | `prevent_destroy = true` lifecycle blocks on all audit stores; 7-year regulatory retention locks enforced via AWS Object Lock. | Write-Once-Read-Many (WORM) compliance storage; raw deletion actions trigger security operations center alarms. |

## 🛠️ Hands-On Exercise: Bounding the Container Deployment Pipeline

**Operational Challenge:** You need a GitHub Action workflow to build and push container images to a private registry. If you prompt an AI model without strict boundaries, the model will generate scripts that use unpinned Docker actions (`@v1`), expose root execution permissions, or hardcode cloud access keys.

**Your Action:** Author a complete 3-Part Directive for this pipeline:
1. **Context Boundary**: Reference `.github/workflows/deploy.yml` and the approved enterprise container registry.
2. **Task Instruction**: Build the container image, run vulnerability scans with Trivy, and push the image tagged with git commit SHA.
3. **Format & Safety Constraints**: Forbid unpinned action versions; mandate rootless container execution; forbid root passwords.
